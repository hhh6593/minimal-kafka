v02 — 디스크 로그 + fsync

유실 재현

브로커 kill 시 page cache에만 있던 레코드 유실.

추가된 것

  • Log 인터페이스 · SegmentedLog 파일 세그먼트 + sparse offset index
  • LogConfig — flushEveryNMessages, flushOnClose
  • Broker.kill() — flush 생략 모사
1분 요약: 디스크에 write했다 ≠ 디스크에 도달했다. write()는 page cache까지. fsync()만 저장 매체까지.

실제 Kafka 대응

설정
log.flush.interval.messages, log.flush.interval.ms
기본값
거의 무한대 — OS page cache + 리플리케이션 의존
안전망
리플리케이션 + acks=all + min.insync.replicas (v10)

시나리오

  • restartAfterCleanShutdown_retainsAllRecords
  • uncleanKillWithoutFsync_losesRecentRecords
  • flushEveryMessage_retainsEverythingEvenOnKill
▶ 실행해보기

1. 자동 테스트

./gradlew :scenarios:test --tests 'mk.scenarios.V02_*'

2. 유실 시나리오 상세

테스트 내부 핵심:

LogConfig lc = LogConfig.segmented(data, 4096)
        .withFlushEvery(Integer.MAX_VALUE)   // fsync 사실상 안 함
        .withFlushOnClose(false);            // 종료 시에도 fsync 없음
Broker broker = new Broker(cfg.withLogConfig(lc));
broker.start();
// ... produce 100건 ...
broker.kill();                                // SIGKILL 시뮬 = uncleanClose

// 재기동 후 읽기 → produced 이하만 보임

3. 직접 실험

  • flushEvery=1로 바꾸고 같은 kill() 수행 → 전 건 보존 확인.
  • BrokerMain을 수정해 스토리지를 SEGMENTED로 바꾸고 실제 kill -9로 죽여보기. build/tmp/ 경로에 .log / .idx 파일 생성 확인.
  • 세그먼트 파일을 hex dump: xxd build/tmp/.../0000000000.log | head — 우리 record format 관찰.

운영 연결

실 Kafka: log.flush.interval.messages, log.flush.interval.ms. 기본값은 거의 무한대 — fsync가 아닌 리플리케이션이 내구성 보증이다 (v10).

v03 — 멀티 파티션 + 파티셔너

핫 파티션

키 편중으로 한 파티션만 바쁨. 나머지 컨슈머 idle.

추가

  • TopicConfig.partitionCount
  • 클라이언트 Partitioner — Hash / RoundRobin / Sticky / Default
핵심: 파티션 = 병렬 단위. 키 설계가 곧 병렬성 설계. 키 종류가 부족하면 파티션을 늘려도 소용 없음.

Kafka 대응

기본 (2.4+)
키 있으면 murmur2 hash, 없으면 sticky (KIP-480)
설정
partitioner.class, partitioner.adaptive.partitioning.enable

흔한 실수

  • 파티션 수 증가 시 키→파티션 매핑 바뀜 → 순서 보장 깨짐
  • null 키 + round-robin으로 배칭 효율 저하 → sticky 전환 (2.4+)
▶ 실행해보기

1. 자동 테스트

./gradlew :scenarios:test --tests 'mk.scenarios.V03_*'

기대 출력

V03_PartitioningTest > hashPartitioner_sameKeyAlwaysSamePartition() PASSED
V03_PartitioningTest > roundRobin_distributesAcrossPartitions() PASSED

2. 핫 파티션 직접 재현

ProducerConfig cfg = new ProducerConfig()
        .host("127.0.0.1").port(port)
        .partitions(4)
        .partitioner(new Partitioner.Hash());

try (Producer p = new Producer(cfg)) {
    for (int i = 0; i < 1000; i++) {
        String key = (i % 10 == 0) ? "rare" : "hot";
        p.send(ProducerRecord.of("t", key, "v" + i));
    }
}
// 파티션별 consume → 키 2종 → 파티션 2개에 전량 쏠림

3. 실험

  • 파티셔너를 Partitioner.RoundRobin으로 바꾸고 키를 유지한 채 재실행 → 균등 분배 확인.
  • Partitioner.Sticky로 실행 후 sticky.rotate(4) 호출 빈도 조정 → 배치 크기와의 트레이드오프 관찰.
  • 파티션 수를 4 → 8로 늘리고 같은 키로 재배포 → 일부 키가 다른 파티션에 배정되며 순서 보장이 깨지는 현상.

v04 — 프로듀서 배칭 + acks

게챠

linger.ms 켜면 send()가 돌려주는 offset은 -1. 흔한 혼동 지점.

트레이드오프

knob작게크게
linger.ms저지연고처리량, 지연 ↑
batch.size작은 배치 다수적은 배치, 개당 큼
acks0/1 빠름, 위험all 안전, 지연
retries빠른 실패복원력 ↑, 순서 리스크
주의: max.in.flight.requests.per.connection > 1 + retries → 순서 역전 가능.
▶ 실행해보기

1. 자동 테스트

./gradlew :scenarios:test --tests 'mk.scenarios.V04_*'

2. sentinel offset 게챠 관찰

ProducerConfig cfg = new ProducerConfig().host("127.0.0.1").port(port)
        .lingerMs(50).batchSize(1024);         // linger ON
try (Producer p = new Producer(cfg)) {
    var md = p.send(ProducerRecord.of("t", "m0"));
    System.out.println(md.offset());           // -1  ← 아직 flush 전, 실제 offset 미확정
    p.flush();
    // 이 시점 이후에야 broker에 도달
}

실 Kafka도 linger/배칭으로 send()는 Future<RecordMetadata>를 반환해 flush 전에 offset을 알 수 없다 — 동일한 게챠.

3. 실험

  • lingerMs=1000000, batchSize=64로 설정 → size 기반 flush만 작동. 작은 레코드를 많이 보내면 size 초과 시점에 덩어리로 flush.
  • retries=3 상태에서 브로커 다운시키고 send → 재시도 백오프 로그 확인.
  • 배칭 켠 상태로 produce → broker 로그에서 baseOffset이 여러 건씩 묶여 찍히는 것 확인 (logEndOffset - baseOffset = 배치 크기).

v05 — 멱등 프로듀서

OUT_OF_ORDER

PID + epoch + 파티션별 seq. 재시도 중 중복 또는 OUT_OF_ORDER_SEQUENCE_NUMBER.

추가

  • INIT_PRODUCER_ID API
  • ProducerStateManager — (pid, topic, partition) → lastSeq
  • PRODUCE 요청에 producerId, producerEpoch, baseSequence 동봉

자주 혼동

  • "멱등 = exactly-once" — 아니오. 멱등은 프로듀서→브로커 구간만. EOS는 트랜잭션 필요.
  • 프로듀서 재시작 시 새 PID → 과거 seq와 무관
▶ 실행해보기

1. 자동 테스트

./gradlew :scenarios:test --tests 'mk.scenarios.V05_*'

2. OUT_OF_ORDER 직접 터뜨리기

ProducerConfig cfg = new ProducerConfig().host("127.0.0.1").port(port).idempotence(true);
try (Producer p = new Producer(cfg)) {
    p.send(ProducerRecord.of("t", "m0"));        // seq=0 accepted

    // broker 측 seq를 인위적으로 5로 점프시킨 뒤 send
    broker.api().producerState()
        .advance(p.producerId(), "t", 0, /*baseSeq*/ 5, /*count*/ 1);

    p.send(ProducerRecord.of("t", "m1"));
    // → broker error: OUT_OF_ORDER_SEQUENCE_NUMBER expected=1 got=6
}

3. 실험

  • idempotence 끄고 retries=3 설정 + 브로커를 중간에 killing으로 재시도 유도 → 같은 레코드가 두 번 기록되는지 consumer로 확인.
  • idempotence 켜고 같은 상황 재현 → 브로커가 duplicate를 거부하는 모습. (현재 구현상 broker는 seq gap만 감지, 완전한 중복 거부는 실 Kafka에서만)

v06 — 컨슈머 poll 루프

리밸런스 루프

처리 느려서 강퇴 → 재조인 → 또 강퇴. 무한 리밸런스.

GC pause 함정: JVM full GC 3s → 하트비트 빠짐. session.timeout 45s면 안전. 그러나 max.poll.interval은 메인 스레드 기준이라 GC 영향 받음.

수정 전략

  1. 처리를 max.poll.records로 쪼개기
  2. 실제 처리 로직을 별도 스레드로 분리
  3. long-running 처리 불가피하면 max.poll.interval.ms를 늘리되, 리밸런스 회복 지연 수용
▶ 실행해보기

1. 자동 테스트

./gradlew :scenarios:test --tests 'mk.scenarios.V06_*'

2. 강퇴 상황 재현

ConsumerConfig cfg = new ConsumerConfig().host("127.0.0.1").port(port)
        .group("g").subscribe("t")
        .sessionTimeout(100).heartbeat(30);     // 매우 짧게

try (GroupConsumer c = new GroupConsumer(cfg)) {
    int genBefore = c.generation();            // e.g. 1
    c.poll(100);

    Thread.sleep(250);                          // sessionTimeout 초과 처리
    broker.api().coordinator()
          .expireDeadMembers(System.currentTimeMillis());   // 코디네이터가 강퇴

    c.poll(100);                                // 다음 poll에서 UNKNOWN_MEMBER_ID
    System.out.println(c.generation());         // 2+ — rejoin 발생
}

3. 실험

  • sessionTimeout을 넉넉히(5000ms) 두고 같은 sleep(250) → rejoin 없음.
  • poll 사이 sleep을 점진적으로 늘리며 "리밸런스 임계점" 탐색.
  • 현재 GroupConsumer는 싱글 스레드. 실제 Kafka처럼 백그라운드 heartbeat 스레드를 추가하면 어떤 문제가 완화되고 어떤 문제는 그대로인지 생각해보기 (답: max.poll.interval.ms는 여전히 메인 스레드 기준).

v07 — k8s 롤링 리스타트 리밸런스 스톰

전체 멈춤

10 pod 롤링 → 매번 리밸런스 → 전체 소비 멈춤.

해결: static membership (KIP-345)

설정
group.instance.id=<id>
효과
close + 재기동이 session.timeout 안이면 리밸런스 없이 동일 assignment 유지
함정
static id 중복 → FENCED_INSTANCE_ID
대안
cooperative sticky (KIP-429) — 리밸런스를 2단계로 분할

재현 결과

  • rollingRestartWithoutStaticMembership_rebalancesEveryTime — 제너레이션 20+ 번 bump
  • rollingRestartWithStaticMembership_avoidsRebalance — 4 미만 bump
▶ 실행해보기

1. 자동 테스트

./gradlew :scenarios:test --tests 'mk.scenarios.V07_*'

2. 스톰 직접 관찰

int n = 10;
List<GroupConsumer> pods = new ArrayList<>();
for (int i = 0; i < n; i++) {
    pods.add(new GroupConsumer(new ConsumerConfig().host("127.0.0.1").port(port)
            .group("g").subscribe("t")));
}
int gen0 = pods.get(n - 1).generation();

// 롤링 리스타트 시뮬
for (int i = 0; i < n; i++) {
    pods.get(i).close();                                       // LEAVE → gen++
    pods.set(i, new GroupConsumer(new ConsumerConfig()...));   // JOIN → gen++
}
int gen1 = pods.get(n - 1).generation();
System.out.println("bumps = " + (gen1 - gen0));                // ≥20

3. static membership로 완화

new ConsumerConfig()...
    .staticId("pod-" + i)            // ← 이것만 바꾸면
    .subscribe("t")
// close()에서 LEAVE를 안 보내고, JOIN은 같은 member로 재사용 → 리밸런스 <= 3

4. 실험

  • pod 수를 50으로 늘려 bump 폭증 관찰.
  • 절반만 static, 절반은 일반 → 부분 스톰 관찰 (실 운영에서 흔한 하이브리드).
  • 두 번째 static instance를 같은 id로 시작 → FENCED_INSTANCE_ID 에러 재현은 본 구현 범위 밖.

v08 — 파티션 assignor 비교

4 PASS
assignor장점단점
range토픽 내 키 범위 직관파티션 수 홀수일 때 skew
roundrobin다수 토픽 균등리밸런스 시 재배치 범위 큼
sticky리밸런스 최소화구현 복잡
cooperative-sticky2단계 리밸런스이전 assignor 혼용 불가
새 프로토콜: KIP-848 — broker-side assignment, Kafka 4.x 기본.
▶ 실행해보기

1. 자동 테스트

./gradlew :scenarios:test --tests 'mk.scenarios.V08_*'

2. assignor 직접 비교

Map<String,Integer> topics = Map.of("t1", 7);
List<String> members = List.of("c1", "c2", "c3");
Map<String,List<String>> subs = Map.of("c1",List.of("t1"),"c2",List.of("t1"),"c3",List.of("t1"));

Assignors.range      (topics, members, subs);        // c1=3, c2=2, c3=2 (skew)
Assignors.roundRobin (topics, members, subs);        // 균등
Assignors.sticky     (topics, members, subs, prev);  // 이전 유지 + 균형

3. 실험

  • 파티션 수를 11로, 멤버를 3으로 해 range skew 최대화.
  • sticky에 previousPlan 넘기고 한 멤버 제거 → 제거되지 않은 멤버의 assignment 얼마나 유지되는지 측정.
  • cooperative-sticky 2단계 리밸런스(revoke → assign)는 본 구현에서 단일 패스로 접혀 있음. 실 Kafka 로그에서 두 번의 JoinGroup이 어떻게 찍히는지 비교.

v09 — 오프셋 커밋 시멘틱

skip / 중복

auto commit 중 예외 → skip. 또는 수동 커밋 타이밍 틀려 중복.

시멘틱 결정 매트릭스

보장커밋 전략
at-most-once처리 전 커밋 → 실패 시 skip

v15-1 — 좀비 트랜잭션 (KIP-890)

희귀

트랜잭션 commit 후 지연된 send가 같은 PID/epoch로 수락돼 다음 트랜잭션에 섞임.

근본 원인

수정

  • transaction.version=2 (4.0+ 자동 활성)
  • 매 commit/abort 시 epoch bump → 이전 epoch write 거부
  • 4.0+ 클라이언트 필요
검증된 출처
  • KIP-890: Transactions Server-Side Defense
  • Umbrella JIRA: KAFKA-14402
  • Current 2024 — Fortifying Your Transactions with KIP-890

2. 좀비 write 직접 확인

v15-5 — 티어드 스토리지 cold read (KIP-405)

2. cold vs tail 비교

broker.api().toggles().coldReadBoundaryOffset = 80;    // offset < 80 = cold
broker.api().toggles().coldReadDelayMs        = 50;    // 50ms 주입

// cold read
long t0 = System.currentTimeMillis();
try (Consumer c = new Consumer("127.0.0.1", port, "t", 0, 0L)) { c.poll(5); }
System.out.println("cold: " + (System.currentTimeMillis() - t0) + "ms");  // ≥50

// tail read
t0 = System.currentTimeMillis();
try (Consumer c = new Consumer("127.0.0.1", port, "t", 0, 90L)) { c.poll(5); }
System.out.println("tail: " + (System.currentTimeMillis() - t0) + "ms");  // <10

실험

  • tail consumer와 cold consumer를 동시에 돌려 "이웃 영향"을 관찰. 브로커가 같은 스레드풀을 공유하면 tail의 p99이 튐.
  • cold 지연을 500ms로 올려 S3 수준 모사 → 운영에서 왜 "backfill 분리 클러스터"를 쓰는지 감 얻기.

v15-6 — Fetch session eviction 스톰 (KIP-227)

CPU 폭증

컨슈머 수가 캐시 슬롯 초과 → 일부가 매 fetch마다 전체 파티션 리스트 재전송. 브로커 CPU/네트워크 폭증.

수정

  • 브로커 max.incremental.fetch.session.cache.slots 증가 (기본 1000)
  • follower fetch 세션 privileged 비트로 우선 보장
  • KAFKA-17182: AsyncKafkaConsumer 축출 빈발 버그 수정 진행

2. LRU 축출 직접 관찰

FetchSessionCache cache = new FetchSessionCache(4);      // 슬롯 4개

for (int i = 0; i < 4; i++) cache.touch("fetcher-" + i);  // 모두 miss (처음)
System.out.println(cache.evictions());   // 0

cache.touch("fetcher-4");                                  // LRU(fetcher-0) 축출
System.out.println(cache.evictions());   // 1

cache.touch("fetcher-0");                                  // miss — full fetch 회귀
System.out.println(cache.evictions());   // 2  (thrashing)

3. 실험

  • capacity를 1000으로 늘리고 100 fetcher로 돌림 → evictions=0.
  • capacity=50, fetcher=60으로 설정 → 지속적 thrashing. 현업에서 JMX IncrementalFetchSessionEvictionsPerSec이 지속 증가하면 이 상태.
