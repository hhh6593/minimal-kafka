minimal-kafka 전체 라이프사이클

한 번의 Produce → Fetch 왕복이 시스템을 어떻게 통과하는지부터 본다. 이 흐름이 모든 버전의 공통 baseline이며, 이후 각 버전은 이 경로의 특정 구간을 확장하거나 고장 낸다.

1) 브로커 기동

new Broker(KafkaConfig.defaults().withPort(0)).start();
// 내부에서 벌어지는 일:
// - LogManager 생성 (스토리지 엔진 선택, 디스크 스캔 v2+)
// - ApiHandler 생성 (GroupCoordinator, OffsetStore, ProducerStateManager 동봉)
// - Acceptor.start()
//   - ServerSocketChannel bind
//   - accept 전용 1 스레드 + IO ThreadPool (기본 64) 시작
//   - boundPort 확정 (port=0이면 OS 할당)

2) Produce 요청의 여정

// client 측
Producer p = new Producer(cfg);
p.send(ProducerRecord.of("demo", "k1", "hello"));
// 1. Partitioner → 파티션 결정
// 2. (idempotence on이면) PID/epoch/baseSequence 첨부
// 3. JSON 프레임 = 4B big-endian length + JSON payload
// 4. 블로킹 소켓으로 1 요청 전송

// broker 측
// 5. Acceptor.accept() → SocketChannel → IO ThreadPool.submit(ConnectionHandler)
// 6. ConnectionHandler.run():
//    - Wire.readFrameBlocking(channel) → JsonNode
//    - ApiHandler.handle(req)
//      → switch("PRODUCE") → handleProduce()
//      → (idempotence) ProducerStateManager.check()
//      → LogManager.getOrCreate(topic, partition) → Log
//      → log.append(batch) → baseOffset
//      → (v10+) ReplicaManager.onAppend(tp, newLeo) → HWM 재계산
//    - Wire.writeFrameBlocking(response)
//    - 연결 유지, 다음 요청 읽기

3) Consumer 그룹의 여정 (v7+)

GroupConsumer c = new GroupConsumer(cfg);
// 생성자 내부:
// - JOIN_GROUP → GroupCoordinator.handleJoinGroup()
//   - memberId 할당, generation++
//   - leader 지정 (memberId 사전순 첫 번째)
// - (leader만) METADATA → 파티션 수 조회 → Assignors.X(...) 호출 → plan
// - SYNC_GROUP (leader의 plan, 또는 빈 요청)
//   → GroupCoordinator가 멤버별 assignment 반환
//
// 각 poll():
// - HEARTBEAT (실패 시 rejoin)
// - 할당 파티션별 FETCH
// - autoCommit=true면 OFFSET_COMMIT

4) 종료

broker.close()  → Acceptor 중지 + LogManager.close (fsync)
broker.kill()   → Acceptor 중지 + LogManager.uncleanClose (fsync 생략, SIGKILL 시뮬)
이 라이프사이클의 핵심: Produce/Fetch가 블로킹 JSON RPC 하나씩 처리되며 모든 서버사이드 상태가 in-proc 객체에 저장된다. 실제 Kafka도 같은 계층 구분을 갖지만 각 레이어가 훨씬 더 깊고 비동기/파이프라인화되어 있다.

이 문서 읽는 법

각 컴포넌트 섹션은 4개 블록으로 구성된다.

우리 구현

실제 코드 스니펫과 파일 경로. 클래스/메서드/필드가 왜 존재하는지.

실제 Kafka

대응되는 Apache Kafka 4.2.0 클래스 / 설정키.

단순화한 것

학습 목적에 안 필요해 의도적으로 잘라낸 부분.

유지한 핵심

잘라내도 이것은 남겨야 시나리오가 교육적 가치를 갖는 부분. 핵심 "판단 포인트".

코드 포인트

관심 있는 동작을 찾으려면 어느 파일 어느 줄을 보라.

자주 틀리는 오진

이 구조를 본 사람이 현업에서 헷갈리는 지점.

처음 읽는다면 위에서 아래로 순서대로 따라가면 자연스럽게 Kafka 라이프사이클을 훑게 된다. 특정 시나리오가 궁금하면 해당 컴포넌트 섹션으로 점프.

Broker 파사드

broker/Broker.java

브로커의 "얼굴". 내부 컴포넌트를 조립하고 외부에는 start() / close() / kill()만 노출한다.

우리 구현

public final class Broker implements AutoCloseable {
    private final KafkaConfig config;
    private final LogManager logs;
    private final ApiHandler api;
    private final Acceptor acceptor;

    public Broker(KafkaConfig config) {
        this.config   = config;
        this.logs     = new LogManager(config.logConfig());
        this.api      = new ApiHandler(logs);
        this.acceptor = new Acceptor(config, api);
    }
    public void start() throws IOException { acceptor.start(); }
    public void close() { acceptor.close(); logs.close(); }
    /** v2 scenario hook: SIGKILL-like unclean shutdown. */
    public void kill()  { acceptor.close(); logs.uncleanClose(); }
}

설계 이유

  • 생성자에서 전부 와이어링: DI 프레임워크 없이 new로 조립. 어떤 객체가 어떤 객체를 소유하는지 즉시 보임.
  • kill()은 교육용 훅: v2 시나리오에서 unclean shutdown을 재현하려면 fsync를 건너뛰고 close해야 함. 실제 프로세스 SIGKILL을 JVM 내에서 테스트하기 어려우므로 "의도된 뒷문"을 설치.
  • api() / logs() 게터 공개: 시나리오 테스트가 브로커 내부 상태(토글, 프로듀서 상태, 오프셋 저장소)를 직접 조작하기 위해 필요. 프로덕션이라면 감추어야 할 것을 일부러 뚫어둠.

실제 Kafka 대응

kafka.server.KafkaBroker (KRaft) / KafkaServer (ZK legacy). 실 구현은 SocketServer, KafkaRequestHandlerPool, ReplicaManager, GroupCoordinator, TransactionCoordinator, DelegationTokenManager, QuotaManagers, LogManager, KafkaController, KafkaScheduler 등을 조립하고 AdminManager, AutoTopicCreationManager, MetadataCache, BrokerTopicStats, HealthCheck까지 와이어링.

단순화

Scheduler, Quota, TxnCoordinator, AdminManager, MetadataCache 등 10+ 서브시스템 제거. close 절차도 graceful shutdown timer 없이 즉시 중단.

핵심

"브로커 = 네트워크 + 로그 + API 핸들러"라는 3층 구조와 start/close 수명 주기의 명시성.

Kafka 대응

KafkaBroker#startup() 순서와 동일한 방향: 로그 → 메타데이터 → 네트워크.

네트워크 계층: Acceptor + ConnectionHandler

broker/network/*

블로킹 NIO. 1 acceptor 스레드 + N IO 스레드 풀. 실제 Kafka의 SocketServer 구조를 단일 단계로 축약.

Acceptor.start() 핵심

server = ServerSocketChannel.open();
server.socket().setReuseAddress(true);
server.bind(new InetSocketAddress(config.host(), config.port()));
boundPort = server.socket().getLocalPort();
server.configureBlocking(true);

ioPool     = Executors.newFixedThreadPool(config.numIoThreads(), namedFactory("mk-io"));
acceptLoop = Executors.newSingleThreadExecutor(namedFactory("mk-acceptor"));
acceptLoop.submit(this::loop);

// loop():
while (running.get()) {
    SocketChannel ch = server.accept();   // 블로킹
    ioPool.submit(new ConnectionHandler(ch, api));
}

ConnectionHandler.run() 핵심

try (SocketChannel ch = channel) {
    ch.configureBlocking(true);
    while (ch.isOpen()) {
        JsonNode req;
        try { req = Wire.readFrameBlocking(ch); }
        catch (EOFException eof) { break; }       // 클라이언트 close
        JsonNode resp = api.handle(req);
        Wire.writeFrameBlocking(ch, resp);
    }
}

단순화

파이프라인 / 셀렉터 / non-blocking IO 전부 제거. 연결당 1 스레드가 read→handle→write를 순차 반복.

핵심

"accept 전담 스레드 + IO 작업용 스레드풀" 분리는 유지. queued.max.requests·num.io.threads의 개념적 출발점.

Kafka 대응

kafka.network.SocketServer의 Acceptor + N Processor (네트워크 스레드) + KafkaRequestHandlerPool (M IO 스레드) 3층 구조.

왜 연결당 스레드?

교육적 명료성. 연결 수 × 스레드 수로 O(N) 자원을 쓰지만, 한 스레드의 스택만 읽으면 "이 커넥션에서 무슨 일이 벌어지는지" 완전히 파악된다. 실제 Kafka는 셀렉터 기반이라 스택 트레이스만으로 흐름 추적이 훨씬 어렵다.

시나리오 함정: 기본 IO 스레드 64개. v7(10 consumers)에서 2로 두었더니 데드락(블로킹 핸들러가 풀을 독점). 이 때문에 KafkaConfig.defaults().numIoThreads=64로 올렸다. 실제 Kafka는 이런 이유로 num.io.threads 튜닝이 운영 주제가 된다.

와이어 프로토콜

broker/protocol/Wire.java

4B big-endian length prefix + JSON payload. tcpdump -A로 평문 확인 가능.

public static JsonNode readFrameBlocking(SocketChannel ch) throws IOException {
    ByteBuffer header = ByteBuffer.allocate(4);
    readFully(ch, header);
    int len = header.flip().getInt();
    if (len <= 0 || len > MAX_FRAME_BYTES) throw new IOException("bad frame length " + len);
    ByteBuffer body = ByteBuffer.allocate(len);
    readFully(ch, body);
    return JSON.readTree(body.flip().array());
}

단순화

ApiKey short, ApiVersion short, correlationId int, clientId string 제거. schema-per-version 시스템 없음. 바이너리 struct 없음.

핵심

길이 prefix + 구조화된 바디. 실제 Kafka 와이어 프레이밍과 동일한 "Length-delimited messaging" 골격.

Kafka 대응

org.apache.kafka.common.protocol.Protocol, RequestHeader, ApiMessageType. 각 Api마다 버전별 Schema 정의.

v4에서 바이너리로 전환 예정이었던 이유

계획: 실 kafka-clients 4.2.0이 우리 브로커에 붙어 들어올 수 있도록 Produce v9, Fetch v13 등을 서브셋 구현. 본 저장소에서는 교육 효과 대비 구현 비용이 커서 JSON 유지. 바이너리 전환은 어떻게와 왜의 탐구 포인트로만 남긴다.

ApiHandler — 단일 라우터

broker/api/ApiHandler.java

들어오는 요청의 "api" 필드로 switch. 각 케이스에서 담당 서브시스템에 위임.

public JsonNode handle(JsonNode req) {
    String api = req.path("api").asText("");
    try {
        return switch (api) {
            case ApiKeys.PRODUCE          -> handleProduce(req);
            case ApiKeys.FETCH            -> handleFetch(req);
            case ApiKeys.METADATA         -> handleMetadata();
            case ApiKeys.CREATE_TOPIC     -> handleCreateTopic(req);
            case ApiKeys.INIT_PRODUCER_ID -> producers.handleInitProducerId(req);
            case ApiKeys.FIND_COORDINATOR -> coordinator.handleFindCoordinator(req);
            case ApiKeys.JOIN_GROUP       -> coordinator.handleJoinGroup(req);
            case ApiKeys.SYNC_GROUP       -> coordinator.handleSyncGroup(req);
            case ApiKeys.HEARTBEAT        -> coordinator.handleHeartbeat(req);
            case ApiKeys.LEAVE_GROUP      -> coordinator.handleLeaveGroup(req);
            case ApiKeys.OFFSET_COMMIT    -> offsets.handleCommit(req);
            case ApiKeys.OFFSET_FETCH     -> offsets.handleFetch(req);
            default -> error("unknown api: " + api);
        };
    } catch (Exception ex) {
        LOG.error("handler failed for api={}", api, ex);
        return error(ex.getClass().getSimpleName() + ": " + ex.getMessage());
    }
}

handleProduce 내부 순서

  1. (v5+) ProducerStateManager.check(pid, epoch, topic, partition, baseSeq, count) — 멱등성 검증
  2. records 디코드 (base64 → Batch.Entry)
  3. LogManager.getOrCreate(topic, partition) — 로그 얻기
  4. log.append(entries) — baseOffset 반환
  5. (v5+) producers.advance(...) — seq 전진
  6. 응답: {ok, topic, partition, baseOffset, logEndOffset}

handleFetch 내부 순서

  1. (v15-5) coldReadDelayMs 토글 검사 → Thread.sleep() 주입
  2. LogManager.get(topic, partition) — 없으면 빈 응답
  3. log.read(offset, maxRecords)
  4. records 인코드 + highWatermark 반환

단순화

ApiVersions 네고, 권한 검사, 쿼터, 버전별 schema 분기 전부 제거. switch 분기 10개가 전부.

핵심

"단일 진입점에서 api 태그로 서브시스템 dispatch" — 실 Kafka의 KafkaApis와 동일한 설계 원칙.

Kafka 대응

kafka.server.KafkaApis#handle(RequestChannel.Request) — 60+ api 처리.

Log 인터페이스

broker/log/Log.java

스토리지 엔진 교체 포인트. v1 InMemory / v2+ Segmented.

public interface Log extends AutoCloseable {
    record LogRecord(long offset, long timestamp, byte[] key, byte[] value) {}

    long append(List<Batch.Entry> batch) throws IOException;
    List<LogRecord> read(long fromOffset, int maxRecords) throws IOException;
    long logEndOffset();
    default void flush() throws IOException {}
    default void uncleanClose() throws IOException { close(); }
}

왜 인터페이스?

v2에서 디스크 세그먼트 도입 시 v1 테스트를 깨뜨리지 않으려면 치환 가능한 경계가 필요했다. LogConfig.Storage enum이 이 선택을 결정하고, LogManager가 공장 역할.

단순화

Transactional markers, abort index, leader epoch cache, time index 없음. record format은 단순 encode/decode.

핵심

append-only + monotonic offset + 인덱스로 position 찾기 + flush/uncleanClose 분리. 4개 개념이 실 Kafka 로그 엔진의 뼈대와 동일.

Kafka 대응

kafka.log.UnifiedLog / LogSegment / OffsetIndex. LogRecord 대응은 RecordBatch / Record.

InMemoryLog — v1 기본

broker/log/InMemoryLog.java

ArrayList<LogRecord> + ReentrantLock. 가장 단순한 append-only 로그.

@Override
public long append(List<Batch.Entry> batch) {
    lock.lock();
    try {
        long base = records.size();
        long now = System.currentTimeMillis();
        for (Batch.Entry e : batch) {
            records.add(new LogRecord(records.size(), now, e.key(), e.value()));
        }
        return base;
    } finally { lock.unlock(); }
}

왜 ArrayList?

오프셋 = 인덱스. O(1) read + 파일 I/O 없음으로 v1 시나리오에서 디스크 이슈로부터 격리. 프로세스 종료 = 데이터 전량 증발. 이 "영속성 없음"이 v2의 출발 문제의식이 된다.

SegmentedLog + Segment

broker/log/SegmentedLog.java

실 Kafka 로그 엔진의 축소판. 파일 세그먼트 + sparse offset index.

디스크 레이아웃

data/<topic>-<partition>/
  0000000000.log   record stream, base offset이 파일명
  0000000000.idx   sparse index { relOffset(int) | fileOffset(int) } 엔트리
  0000000512.log   세그먼트 롤 후 다음 파일
  0000000512.idx

append 경로

// SegmentedLog.append()
Segment active = activeSegment();
for (Batch.Entry e : batch) {
    byte[] buf = encode(logEnd, now, e.key(), e.value());
    if (active.size() + buf.length > segmentBytes && active.size() > 0) {
        Segment rolled = Segment.create(dir, logEnd);     // 롤링
        segments.add(rolled);
        active = rolled;
    }
    active.append(logEnd, buf);
    logEnd++;
    pendingSinceFlush++;
}
if (pendingSinceFlush >= flushEveryNMessages) {
    active.flush();                                       // fsync
    pendingSinceFlush = 0;
}

sparse index (v2의 핵심 교훈)

레코드마다 인덱스 엔트리를 만들지 않는다. 대략 4KB (INDEX_INTERVAL_BYTES) 단위로 "이 오프셋은 파일의 이 위치에 있다"를 찍는다. positionFor(offset)은 인덱스에서 가장 가까운 하한을 찾아 해당 위치부터 순차 스캔.

int positionFor(long offset) {
    int pos = 0;
    int relOff = (int)(offset - baseOffset);
    for (int[] e : index) {
        if (e[0] <= relOff) pos = e[1];
        else break;
    }
    return pos;
}

flush vs uncleanClose

public void close() throws IOException {
    if (flushOnClose) for (Segment s : segments) s.flush();
    for (Segment s : segments) s.close();
}
public void uncleanClose() throws IOException {
    // 의도적으로 flush 생략 — SIGKILL / 크래시 시뮬
    for (Segment s : segments) s.close();
}

단순화

mmap 없이 FileChannel positional read. TimeIndex 없음. 레코드 배치 압축 없음. producer state snapshot / leader epoch checkpoint 없음. 세그먼트 삭제 / 컴팩션은 Retention에 위임.

핵심

(1) 세그먼트 롤링 기준, (2) sparse index 전략, (3) fsync 정책 토글, (4) 재기동 시 스캔으로 logEnd 복원 — 4가지가 실 Kafka의 진짜 위험 지점과 정확히 같다.

Kafka 대응

LogSegment, OffsetIndex (memory-mapped), UnifiedLog의 flush 정책 (log.flush.interval.messages/ms).

v15-3 연결: scanLogEnd()가 있기에 재기동 시 logEnd를 복원한다. 하지만 unclean shutdown으로 페이지 캐시 미플러시 상태면 scan 결과가 실제 커밋됐던 오프셋보다 뒤처질 수 있고, 이 상태의 브로커가 다시 ISR에 합류하면 HWM이 되감긴다 — 바로 KIP-903이 해결한 문제.

LogManager + TopicConfig

broker/log/LogManager.java

토픽/파티션 → Log 매핑. 디스크 스캔으로 재기동 시 기존 로그를 연다.

핵심 자료구조

private final LogConfig logConfig;
private final Map<String, TopicConfig> topics = new ConcurrentHashMap<>();
private final Map<TopicPartition, Log> logs = new ConcurrentHashMap<>();

public Log getOrCreate(String topic, int partition) {
    TopicConfig cfg = topics.computeIfAbsent(topic, n -> TopicConfig.defaults(n, 1));
    if (partition >= cfg.partitionCount()) {
        // v1 호환: 자동 파티션 확장
        TopicConfig grown = TopicConfig.defaults(topic, partition + 1);
        topics.put(topic, grown);
    }
    return logs.computeIfAbsent(new TopicPartition(topic, partition), k -> newLog(k));

private void loadFromDisk() {
    Path root = logConfig.dataDir();
    if (root == null || !Files.isDirectory(root)) return;
    try (var stream = Files.list(root)) {
        stream.filter(Files::isDirectory).forEach(dir -> {
            String name = dir.getFileName().toString();
            int dash = name.lastIndexOf('-');
            if (dash <= 0) return;
            String topic = name.substring(0, dash);
            int partition = Integer.parseInt(name.substring(dash + 1));
            // topic-N 디렉터리를 찾아서 SegmentedLog로 자동 오픈
            topics.put(topic, TopicConfig.defaults(topic, partition + 1));
            logs.computeIfAbsent(new TopicPartition(topic, partition), k -> newLog(k));
        });
    } catch (IOException e) { LOG.warn("failed to scan data dir {}", root, e); }
}

State 구조체

public static final class State {
    public volatile int leader = -1;
    public final Set<Integer> replicas = new LinkedHashSet<>();
    public final Set<Integer> isr      = new LinkedHashSet<>();
    public final Map<Integer, Long>    followerLeo  = new ConcurrentHashMap<>();
    public final Map<Integer, Integer> brokerEpoch  = new ConcurrentHashMap<>();
    public volatile long highWatermark = 0;
    public volatile long leo           = 0;

    public synchronized void recomputeHwm() {
        long min = leo;
        for (int f : isr) min = Math.min(min, followerLeo.getOrDefault(f, 0L));
        this.highWatermark = min;
    }
}

growIsr — KIP-903 재현

public synchronized void growIsr(TopicPartition tp, int brokerId, int brokerEpoch,
                                 boolean enforceEpochCheck) {
    State s = states.get(tp);
    if (enforceEpochCheck) {
        Integer known = s.brokerEpoch.get(brokerId);
        if (known != null && brokerEpoch < known) {
            return;  // KIP-903: stale-epoch follower 거부
        }
    }
    s.brokerEpoch.put(brokerId, brokerEpoch);
    s.isr.add(brokerId);
    s.recomputeHwm();
}

electUncleanLeader — 최악 시나리오 선택

public synchronized boolean electUncleanLeader(TopicPartition tp, boolean uncleanEnabled) {
    if (!s.isr.isEmpty()) return true;            // clean 가능
    if (!uncleanEnabled)  return false;           // 파티션 오프라인

    // 교육 목적: 최악의 stale replica 선택 → HWM 최대 되감김 = unclean의 위험 최대화 시연
    int pick = -1;
    long pickLeo = Long.MAX_VALUE;
    for (int r : s.replicas) {
        long leo = s.followerLeo.getOrDefault(r, 0L);
        if (leo < pickLeo) { pick = r; pickLeo = leo; }
    }
    s.leader = pick;
    s.isr.add(pick);
    s.leo = pickLeo; s.highWatermark = pickLeo;
    return true;
}

private int enforceDelete(Log log, TopicConfig cfg) throws Exception {
    long end = log.logEndOffset();
    if (cfg.retentionBytes() <= 0) return 0;
    long approxSize = end * 64L;                          // 간이 추정
    if (approxSize <= cfg.retentionBytes()) return 0;
    long toKeep   = cfg.retentionBytes() / 64L;
    long dropFrom = Math.max(0, end - toKeep);
    return (int) dropFrom;                                // 실제 삭제는 안 함, 개수만 보고
}

private int enforceCompact(Log log) throws Exception {
    var all = log.read(0, (int)Math.min(end, Integer.MAX_VALUE));
    HashSet<String> seenKeys = new HashSet<>();
    int removed = 0;
    for (int i = all.size() - 1; i >= 0; i--) {
        byte[] k = all.get(i).key();
        String ks = k == null ? "__null__" : new String(k);
        if (!seenKeys.add(ks)) removed++;      // 같은 키의 구 버전 카운트
    }
    return removed;
}

단순화

OffsetMap/CleanerThread 없음. tombstone delete.retention.ms 없음. 실제 세그먼트 삭제 / 재쓰기 없음 — 카운트만.

핵심

"리텐션은 시간 기반(delete) 또는 키 기반(compact) 두 축" + "cleaner는 스케줄러가 도는 별도 프로세스"의 개념 이해.

Kafka 대응

LogCleaner, LogCleanerManager, min.cleanable.dirty.ratio.

this.lru = new LinkedHashMap<>(16, 0.75f, true) {     // access-order=true

public synchronized boolean touch(String fetcherId) {
    Boolean existing = lru.get(fetcherId);
    if (existing != null) return true;      // hit = incremental fetch 가능
    lru.put(fetcherId, true);
    return false;                           // miss = 전체 리스트 재전송
}

privileged bit (follower 우선) 없음. 실제 fetch 요청과 연결 없음 — 순수 관찰자.

시나리오 재현 패턴 — 토글 + 훅

broker/api/BrokerToggles.java

"패치 전" vs "패치 후"를 하나의 코드베이스로 모두 재현하기 위해 BrokerToggles를 도입했다.

public final class BrokerToggles {
    public volatile boolean zombieControllerStaleMetadata = false;
    public volatile boolean enforceBrokerEpochOnIsrJoin   = false;   // v15-3 KIP-903
    public volatile boolean resetSequenceOnEpochBumpForAllPartitions = true; // v15-4 fix ON
    public volatile long    coldReadDelayMs        = 0;              // v15-5
    public volatile long    coldReadBoundaryOffset = 0;
    public volatile int     fetchSessionCacheSlots = 1024;           // v15-6
    public volatile boolean uncleanLeaderElectionEnable = true;      // v11
    public volatile long    producerQuotaBytesPerSec = -1L;          // v14
    public volatile int     fetchMaxBytes = Integer.MAX_VALUE;
    public volatile double  compactionMinDirtyRatio = 0.5;
}

왜 이 방식?

  • 단일 코드베이스 유지: 버전별 디렉터리 fork를 피하고, 시나리오 테스트가 broker.api().toggles().X = Y로 시작.
  • "전/후" 대비가 명확: 한 테스트는 false로 버그 재현, 다른 테스트는 true로 수정 검증. 같은 코드, 다른 토글.
  • 프로덕션이라면 하지 말 것: mutable public volatile은 API가 아니다. 교육 목적 한정.

다른 "뒷문" 훅들:

  • Broker.kill() — fsync 생략 close
  • LogManager.uncleanClose() — 브로커 kill의 로그 측 위임
  • GroupCoordinator.expireDeadMembers(nowMs) — 시간 의존성 제거
  • ProducerStateManager.bumpEpoch(pid, withInFlight, resetAll) — 리더 교체 시뮬
  • ReplicaManager의 수동 shrinkIsrDueToLag / growIsr / electUncleanLeader

버전 간 진화 규칙

v1 → v15까지 한 코드베이스가 점진적으로 커졌다. 규칙 3개를 지켰다.

규칙 1 — 인터페이스로 선 긋기

v2에서 Log를 인터페이스로 만들고 InMemoryLog가 그것을 구현하도록 역호환성 있게 리팩토링. 이후 SegmentedLog가 동일 인터페이스로 붙음. v1 테스트는 그대로 통과.

규칙 2 — 설정 토글로 과거 동작 유지

LogConfig.inMemory()가 v1 기본값이어서, v2 도입 후에도 KafkaConfig.defaults()는 여전히 인메모리 로그를 만든다. "과거 동작이 기본"이 핵심.

규칙 3 — 시나리오가 서브시스템을 직접 호출

v10 리플리케이션은 실제 두 브로커 간 네트워크 없이 ReplicaManager 시뮬만 존재. 시나리오가 "브로커 측에서 이런 상태가 되었다고 치자"라고 직접 메서드를 호출. 구현 비용 대비 교육 가치가 가장 높은 지점에만 실 컴포넌트를 두는 전략.

결과: 58개 Java 파일 / 51 테스트 / 15 버전이 단일 빌드로 동작한다. 어떤 버전의 테스트도 다른 버전을 깨뜨리지 않는다.

한계와 열린 질문

  • 실 kafka-clients가 이 브로커에 붙을 수 있게 하려면 Kafka 바이너리 프로토콜 서브셋 필요. 가치 있으나 양이 크다.
  • 실 리플리케이션(두 JVM 프로세스 + 소켓 fetcher) 구현은 "in-proc 시뮬"보다 훨씬 더 많은 실제 이슈를 드러낼 것이다. 다음 큰 확장 포인트.
  • 메트릭 시스템이 없다. JMX가 없어서 "운영자 관점 관찰"은 로그 출력에만 의존.
